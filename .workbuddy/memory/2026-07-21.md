## 完成 5 项优化并修复编译

承接 2026-07-20 的"开始优化"任务，今天把 5 项优化全部落地并打通编译。

### 关键根因（重要！）
本项目的 Swift 6 工具链（Xcode 26.2）**自动成员初始化器（memberwise initializer）不包含带默认值的存储属性**。
- 用 `xcrun swiftc -swift-version 6` 做了最小复现：`struct S { let a: Int; let b: Int = 0 }; S(a:1, b:2)` 报 `extra argument 'b' in call`。
- 之前误判为"ModuleCache 缓存过期"，实际是同一根因：给 `GridPageView.selectedSlotIndex: Int? = nil` 和 `FolderThumbnailView.isSelected: Bool = false` 加了默认值，调用方传这些参数时就报 extra argument。

### 修复方式
- 去掉这两处的默认值，使其变成必填参数（所有调用方本来就传了）：`selectedSlotIndex: Int?`、`isSelected: Bool`。
- `LaunchpadView.targetScreen` 计算属性的 switch 各 case 补上 `return`（否则 getter 缺返回）。
- `LaunchpadWindowController` 滚动监听里 `event.momentumPhase == .none` 是逻辑 bug：`NSEvent.Phase` 是非可选 OptionSet，`.none` 被解析成 `Optional.none` 恒为 false，导致惯性滚动从不被忽略。改为 `event.momentumPhase.isEmpty`。
- `LaunchpadViewModel` 键盘导航里 `idx/newCol/newRow` 从 `var` 改 `let`。
- `AppDelegate` 设置窗口关闭的 `NotificationCenter` 闭包包进 `Task { @MainActor in ... }`，消除 strict concurrency 警告。

### 编译结果
`xcodebuild ... clean build` → **BUILD SUCCEEDED**（仅剩 appintentsmetadataprocessor 的无害工具警告）。

## 辅助功能"已打开但仍显示未授权"的原因与改进

用户反馈：在系统设置开启辅助功能后，设置页仍显示"未授权"。

- **根因（非代码 bug）**：macOS TCC 在**进程启动时**判定辅助功能信任状态。`AXIsProcessTrusted()` 对"开启权限前就已运行"的进程仍返回 false。必须**完全退出 App（⌘Q）并重启**才生效；仅关设置窗口无效。
- **改进**：状态显示包进 `TimelineView(.periodic(from: .now, by: 1.0))`，每秒刷新一次，重启回来后绿点自动亮；并在界面加了一条橙色提示说明"需完全退出并重启"。
- 编译：`xcodebuild clean build` → **BUILD SUCCEEDED**。
- 排查要点：若重启后仍 false，确认拖进列表的是 `Bundle.main.bundleURL`（DerivedData 里的 .app）那一份；ad-hoc 签名在 rebuild 后哈希会变导致授权失效。

## 已授权但按快捷键仍无反应（hotkeyEnabled 默认 false）

用户：辅助功能已授权，但按下全局快捷键不呼出面板。

- **根因**：`setupGlobalHotkey` 的 guard 含 `prefs.hotkeyEnabled`，而 `UserPreferences.hotkeyEnabled` 默认 `defaults.bool(...)` = **false**（"启用快捷键"开关默认关）。所以即使监听能收到按键，guard 直接 return，`toggle()` 从不调用。匹配逻辑本身没问题（setHotkey 与监听端都用同一套 `[.control,.option,.shift,.command]` 交集比较）。
- **修复**：
  1. `hotkeyEnabled` getter 改为"未设置时默认 true"（用 `defaults.object(forKey:) != nil` 判断，尊重用户显式关闭）。
  2. `AppDelegate` 新增 `ensureGlobalHotkey()`（监听为 nil 时重建），并在 `HotkeyPane` 加 `.onChange(of: prefs.hotkeyEnabled)` 打开开关即重建——解决"授权后才开开关/未重启"导致监听为 nil 的边界情形。
  3. 设置面板"全局快捷键" Section：关闭开关时显示橙色提示。
- 编译：`xcodebuild clean build`（已固化 Apple Development 证书，不再带 ad-hoc 参数）→ **BUILD SUCCEEDED**。
- **给用户的关键提示**：改完需重新编译运行。若仍无效，先确认"启用快捷键呼出启动台"开关是开的；再检查菜单栏"打开启动台"是否可用以排除 `toggle()/show()` 本身问题。

## 用户追问：opt+c 大小写是否要大写（hotkey 标签误导）

用户：开关开、菜单栏可用、状态灯绿，但 opt+c 仍不触发；问 c 要大写吗。

## 启动台面板布局优化：去中间空白 + 全屏宽度

用户反馈启动台面板中间空白大、宽度没有撑满全屏。已优化：

- **`GridPageView`**：
  - 用 `GeometryReader` 计算 `cellWidth = (width - 列间距) / 列数`、`cellHeight = (height - 行间距) / 行数`，并加 `.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .top)`，让网格真正铺满整个内容区。

  - `columnCount` 对宽屏更激进：2560+ → 12，1920+ → 9，1440+ → 7，1280+ → 6，其余 5。
  - 新增 `rowCount(for:)` 按屏幕高度自适应：1200+ → 6，900+ → 5，其余 4。

- 编译：`xcodebuild clean build` → **BUILD SUCCEEDED**。

> 注意：一页内应用数量不足时，最后几行会自然空出，空白出现在底部而非中间；行间距和图标大小仍由屏幕尺寸决定。

## 行列数滑块实时生效修复

用户反馈：设置里改"每行列数 / 每页行数"要退出设置页才生效，不能实时预览。

两个根因：
1. **遮挡看不到**：设置浮层是 `LaunchpadView` 内部 `showSettingsOverlay` 浮层，原用 `Color.black.opacity(0.5)` 全屏遮罩 + 居中 520 卡片，把网格盖住压暗，拖动时网格其实在更新但看不见，关掉才发现"生效"。
2. **行列数依赖链不直接**：原来 `LaunchpadView` 用 `@State prefs`，且 `cols/rows` 经 `viewModel.columnCount(for:)` 间接读 `UserPreferences.shared`，不是直接读被观察的 `prefs`。

修复：
- `LaunchpadViewModel` 抽出 `autoColumnCount(for:)` / `autoRowCount(for:)`（只按屏幕宽高自动，不含手动覆盖）；`columnCount`/`rowCount` 改为"override>=3 用指定，否则调 auto*"。
- `LaunchpadView`：`@State prefs` → `@Bindable private var prefs = UserPreferences.shared`；`body` 里 `cols/rows` 直接读 `prefs.columnCountOverride` / `prefs.rowCountOverride`（被 @Bindable 观察）→ 拖动滑块立即重布局。
- `settingsOverlay` 改为**靠右浮层 + `Color.black.opacity(0.25)` 轻遮罩**：左侧网格完整可见，边拖滑块边实时看行列变化；卡片高度随屏幕高度自适应（`max(360, geo.size.height-110)`）。

> 关键结论：让启动台实时响应设置，必须让 `LaunchpadView` 直接观察并读取 `UserPreferences`（用 `@Bindable` 而非 `@State`，且行列数直接用 `prefs.*` 计算），同时避免全屏重遮罩挡住预览区。编译通过 BUILD SUCCEEDED。

## 行列数滑块实时生效（二次修复）

用户再次反馈：拖动"每行列数 / 每页行数"后，网格看起来没有变化，退出设置页才"生效"。

进一步根因：即使 `cols`/`rows` 已经实时变化，**应用图标分页是按旧的 `itemsPerPage` 提前切好的**。`viewModel.layout.pages` 只在启动/扫描时根据当时的 `itemsPerPage` 生成，后续只改 `cols`/`rows` 不会重新分页。因此用户看到的只是每行多塞几个图标，图标不会从第二页自动补到第一页，视觉变化不明显，误以为没生效；退出设置时整视图刷新，才重新按新尺寸显示（但底层仍是旧分页）。

修复：
- `LaunchpadViewModel` 新增 `reflowLayout(to itemsPerPage: Int)`：把所有 page 拍平为 `allItems`，按新 `itemsPerPage` 重新 `chunked`，并钳制 `currentPageIndex` 到新页数范围内，然后 `saveLayout()`。
- `LaunchpadView` 在 `ZStack` 上加 `.onChange(of: cols)` / `.onChange(of: rows)`：行列数任一变化时立即调用 `viewModel.reflowLayout(to: newCols * rows)` / `viewModel.reflowLayout(to: cols * newRows)`，实现真正实时重分页。
- 在 ViewModel 末尾补上 `chunked(into:)` 扩展（与 `GridPageView` 独立，避免跨文件依赖）。

> 设计要点：改行列数不只是改每行/每列显示，必须触发 `layout.pages` 重新切分。否则只是把旧分页的图标在 cell 里重排，图标不会跨页填充，视觉上几乎看不出变化。只有重分页 + 轻遮罩靠右卡片，才能做到真正的边拖边实时预览。编译通过 BUILD SUCCEEDED。

## 设置窗口结构审查（对比 Soluna 的 Settings{ } 场景）

用户问能否用 SolunaApp.swift 那种 `Settings { }` 原生设置窗口结构。审查发现当前项目设置入口有**三套实现、且互相冗余**：

1. `AppLaunchpadApp.body` 已有 `Settings { SettingsView() }` 原生场景（Soluna 同款），仅 ⌘,（系统 App 菜单）能触发；但启动台面板在 `screenSaverWindow-1` 高层级，该原生窗口会**被面板挡住看不见**，所以基本不可用。
2. `AppDelegate.showSettings()`：手动 `NSWindow` 承载 `SettingsView()`，level `.floating`，打开前 `lowerPanelForSettings()` 降面板层级、`willCloseNotification` 里 `restorePanelLevel()` 恢复，presentationOptions 也清理/恢复。**这套已经正确处理了"面板降层让设置窗口可见"的关键难点**，但当前 `onOpenSettings` 闭包形同死代码（没被调用）。
3. `LaunchpadView.showSettingsOverlay`：应用内浮层靠右卡片（用户右键"设置…"实际走这条）。

结论：要"像 Soluna 一样用独立设置窗口"完全可行；唯一前提是打开时把全屏面板降层（已具备）。最干净做法是**统一到一套**：要么走原生 `Settings { }` 场景（菜单/右键调 `NSApp.sendAction(Selector(("showSettingsWindow:")), to:nil, from:nil)` 打开并降面板），要么复用已写好的 `AppDelegate.showSettings()` 专用窗口，然后删掉应用内浮层 `showSettingsOverlay`。两种方案下实时预览都有效（面板只是降层、网格仍可见）。

> **用户决定（本回合）**：不切换成独立窗口，**保留应用内浮层 `showSettingsOverlay`** 作为设置 UI，通过右键"设置…"打开（`LaunchpadView.openSettings()` → `showSettingsOverlay = true`），不需要快捷键。应用内浮层最适合本项目，因为网格在背后始终可见、实时预览最好。
> 后续若清理：可删除冗余的 `AppDelegate.showSettings()` 专用 NSWindow 死代码、`onOpenSettings` 死闭包，以及 `AppLaunchpadApp` 里那个被面板挡住的 `Settings { }` 原生场景（或保留它仅供 ⌘, 触发、但当前因面板高层级其实看不见）。但用户明确说"没有快捷键、重点是应用内浮层"，所以**不要主动去改成独立窗口**。
