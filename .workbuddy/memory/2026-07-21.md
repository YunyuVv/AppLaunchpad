## 诊断：Dock 图标点击行为（文档 ↔ 代码不一致）

- 设计文档（`docs/技术实现/01-架构设计.md` 第251行、`03-功能实现计划.md` 第102行）与早期计划（`docs/superpowers/plans/2026-07-20-phase1-foundation.md` 第212行）都写明 Dock 点击应由 `AppDelegate.applicationShouldHandleReopen` → `toggle()` 来显示/隐藏启动台。
- **实际 `AppDelegate.swift` 并未实现 `applicationShouldHandleReopen`**（已 grep 确认无匹配）。因此：左键点 Dock 只是激活 App，启动台全屏面板（`NSPanel`，由 `LaunchpadWindowController` 管辖）不会弹出；面板只通过 `toggle()`（全局快捷键 / 状态栏菜单 / Dock 右键菜单「打开启动台」）显示。
- 结论：这是一个文档超前/代码未落地的缺口。若想让左键点 Dock 直接呼出启动台，需在 `AppDelegate` 补上 `applicationShouldHandleReopen(_:hasVisibleWindows:) -> Bool { toggle(); return false }`。
- **已修复并编译验证通过**（BUILD SUCCEEDED）：在 `AppDelegate.swift` 的 Dock 区新增 `applicationShouldHandleReopen(_:hasVisibleWindows:) -> Bool { toggle(); return false }`，现在左键点 Dock 即可呼出/收起启动台，与原生 Launchpad 一致。

## 设计决策：设置窗红叉不退出 App

- 用户确认采用"保持常驻"方案：**设置窗口点红叉只关窗，App 不退出**。退出仅 `⌘Q` / 状态栏菜单「退出 AppLaunchpad」。
- **根因修正（重要）**：App 的 `body` 只有唯一的 `Window("设置", id: "settings")` 场景。SwiftUI 会把孤零零的 `Window(id:)` 当成主窗口——① 启动自动打开设置窗；② 关闭它时按"单一主窗口 App"逻辑直接退出（默认 `applicationShouldTerminateAfterLastWindowClosed`=false 在这个场景下拦不住）。
- **修复（BUILD SUCCEEDED）**：
  1. `AppLaunchpadApp.swift` 给设置 Scene 加 `.defaultLaunchBehavior(.suppressed)` → 启动/重启不再自动打开设置窗（仅 ⌘, / 菜单按需打开）。
  2. `AppDelegate.swift` 显式实现 `applicationShouldTerminateAfterLastWindowClosed` 返回 `false` → 关设置窗不退出，落实"保持常驻"。
- 注：`.suppressed` 是 macOS 15+ API，本项目部署目标 26.0，可用。修正了上一轮"默认 false 已够用、无需改代码"的错误判断。

## 修复：Dock 右键「设置…」打不开设置窗口

- **根因**：`openSettings()` 用 `NSApp.sendAction(Selector("showWindow:"), to: nil)` 打开设置窗。`showWindow:` 是 AppKit `NSWindowController` 动作，依赖响应者链；对 SwiftUI `Window(id:)` 场景不可靠（窗口未开时链上无对应控制器，Dock 菜单触发时 App 非 key/first responder → 动作被丢弃）。之前能看到设置窗是因为 `Window(id:)` 启动自动弹出，从没真正靠 `showWindow:` 手动打开过；加 `.suppressed` 不再自动弹后问题才暴露。
- **修复（BUILD SUCCEEDED）**：改用 SwiftUI 环境的 `openWindow(id: "settings")`。
  - `AppLaunchpadApp.swift`：`@Environment(\.openWindow)` 捕获，body 里 `appDelegate.setSettingsOpener { self.openWindow(id: "settings") }` 注入；⌘, 的 Button 也直接用 `openWindow(id:)`。
  - `AppDelegate.swift`：新增 `settingsOpener: (@MainActor () -> Void)?` 与 `setSettingsOpener`，`openSettings()` 改调 `settingsOpener?()`（fallback 才用 `showWindow:`）。保留自定义 `Window(id:)` 外观。
- **结论**：打开 SwiftUI `Window(id:)` 场景必须用 `openWindow(id:)`，别用 `showWindow:`。

### 关键根因（重要！）
本项目的 Swift 6 工具链（Xcode 26.2）**自动成员初始化器（memberwise initializer）不包含带默认值的存储属性**。
- 用 `xcrun swiftc -swift-version 6` 做了最小复现：`struct S { let a: Int; let b: Int = 0 }; S(a:1, b:2)` 报 `extra argument 'b' in call`。
- 之前误判为"ModuleCache 缓存过期"，实际是同一根因：给 `GridPageView.selectedSlotIndex: Int? = nil` 和 `FolderThumbnailView.isSelected: Bool = false` 加了默认值，调用方传这些参数时就报 extra argument。

### 修复方式
- 去掉这两处的默认值，使其变成必填参数（所有调用方本来就传了）：`selectedSlotIndex: Int?`、`isSelected: Bool`。
- `LaunchpadView.targetScreen` 计算属性的 switch 各 case 补上 `return`（否则 getter 缺返回）。
- `LaunchpadWindowController` 滚动监听里 `event.momentumPhase == .none` 是逻辑 bug：`NSEvent.Phase` 是非可选 OptionSet，`.none` 被解析成 `Optional.none` 恒为 false，导致惯性滚动从不被忽略。改为 `event.momentumPhase.isEmpty`。
- `LaunchpadViewModel` 键盘导航里 `idx/newCol/newRow` 从 `var` 改 `let`。
- `AppDelegate` 设置窗口关闭的 `NotificationCenter` 闭包包进 `Task { @MainActor in ... }`，消除 strict concurrency 警告。

### 编译结果
`xcodebuild ... clean build` → **BUILD SUCCEEDED**（仅剩 appintentsmetadataprocessor 的无害工具警告）。

## 辅助功能"已打开但仍显示未授权"的原因与改进

用户反馈：在系统设置开启辅助功能后，设置页仍显示"未授权"。

- 编译：`xcodebuild clean build` → **BUILD SUCCEEDED**。
- 排查要点：若重启后仍 false，确认拖进列表的是 `Bundle.main.bundleURL`（DerivedData 里的 .app）那一份；ad-hoc 签名在 rebuild 后哈希会变导致授权失效。

## 已授权但按快捷键仍无反应（hotkeyEnabled 默认 false）

用户：辅助功能已授权，但按下全局快捷键不呼出面板。

- **根因**：`setupGlobalHotkey` 的 guard 含 `prefs.hotkeyEnabled`，而 `UserPreferences.hotkeyEnabled` 默认 `defaults.bool(...)` = **false**（"启用快捷键"开关默认关）。所以即使监听能收到按键，guard 直接 return，`toggle()` 从不调用。匹配逻辑本身没问题（setHotkey 与监听端都用同一套 `[.control,.option,.shift,.command]` 交集比较）。

  1. `hotkeyEnabled` getter 改为"未设置时默认 true"（用 `defaults.object(forKey:) != nil` 判断，尊重用户显式关闭）。
  2. `AppDelegate` 新增 `ensureGlobalHotkey()`（监听为 nil 时重建），并在 `HotkeyPane` 加 `.onChange(of: prefs.hotkeyEnabled)` 打开开关即重建——解决"授权后才开开关/未重启"导致监听为 nil 的边界情形。
  3. 设置面板"全局快捷键" Section：关闭开关时显示橙色提示。
- 编译：`xcodebuild clean build`（已固化 Apple Development 证书，不再带 ad-hoc 参数）→ **BUILD SUCCEEDED**。
- **给用户的关键提示**：改完需重新编译运行。若仍无效，先确认"启用快捷键呼出启动台"开关是开的；再检查菜单栏"打开启动台"是否可用以排除 `toggle()/show()` 本身问题。

## 启动台面板布局优化：去中间空白 + 全屏宽度

用户反馈启动台面板中间空白大、宽度没有撑满全屏。已优化：

- **`GridPageView`**：
  - 用 `GeometryReader` 计算 `cellWidth = (width - 列间距) / 列数`、`cellHeight = (height - 行间距) / 行数`，并加 `.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .top)`，让网格真正铺满整个内容区。

- **`LaunchpadView`**：
  - `effectiveIconSize` 去掉原来的 120 硬上限，改为 `min(cellW*0.74, cellH*0.7, 160)`；`sidePad` 从 60 收窄到 40，让图标区域更接近屏幕边缘。

  - 搜索页和分页视图都传入 `rows` 参数。
- **`LaunchpadViewModel`**：
  - `columnCount` 对宽屏更激进：2560+ → 12，1920+ → 9，1440+ → 7，1280+ → 6，其余 5。
  - 新增 `rowCount(for:)` 按屏幕高度自适应：1200+ → 6，900+ → 5，其余 4。
  - `itemsPerPage` 改为 `columnCount * rowCount`（按实际屏幕计算）。
- 编译：`xcodebuild clean build` → **BUILD SUCCEEDED**。

## 诊断：UserPreferences 的 @Observable 实际失效（设置页两 bug 的统一根因）

用户反馈：①设置页「恢复默认」点后当前页不刷新，切走再切回才显示默认；②外观滑块拖动，设置标签与启动台界面均无实时变化。

- **根因**：`UserPreferences` 所有偏好属性都是「计算属性 + UserDefaults 支撑」（get/set 直接读 `defaults`），**没有任何被 @Observable 追踪的存储属性**。SwiftUI Observation 只追踪"存储属性"的变化；计算属性若无内部读取被追踪的存储属性，则完全不触发视图重绘。于是改属性只写 UserDefaults、不发变更通知，所有读 `prefs.xxx` 的视图（Settings 各 Pane、LaunchpadView、BackgroundView）都不会刷新。
- **佐证**：同类 `var isCapturingHotkey: Bool = false` 是存储属性，确实能驱动全局监听逻辑；而 prefs.* 全是 computed，不工作。代码注释"被 @Bindable 观察，保证实时刷新"是错误假设（@Bindable 只能观察存储属性）。
- **修复方向（未改代码，待确认）**：把每个属性改为存储属性——`init` 中从 defaults 载入，`didSet`/`set` 写回 defaults（或保留计算属性接口、内部加私有存储后盾 `_x` 并由 getter 读 `_x`）。这样 Observation 真正生效，① 当前页即刷新、② 启动台实时变化，两个 bug 一并解决。
- **待更正**：MEMORY.md 里"由于 UserPreferences 是 @Observable，设置面板和启动台界面会同步刷新"这条断言是错的，落地修复时应一并更正。

## 修复落地：UserPreferences 改为存储属性（两 bug 一并解决）

## 拖到第二页卡死修复（2026-07-21，BUILD SUCCEEDED）

现象：拖拽 app 到屏幕边缘触发自动翻页到第二页后，拖拽"卡死"、浮动图标不动、无法继续移动。

### 根因
`LaunchpadView.pagingView` 给 `GridPageView` 加了 `.id(viewModel.currentPageIndex)` + `.transition`（翻页滑动动画）。拖拽手势挂在**每页 `GridPageView` 内部的图标**上；边缘 `edgeScrollTimer` 触发 `goToNextPage()` → `currentPageIndex` 变化 → `.id` 改变 → SwiftUI 把旧 `GridPageView`（连同正在拖拽的图标与其手势）整个**销毁重建**。进行中的拖拽手势因宿主视图被移除而被系统取消 → `onChanged` 不再触发 → `dragState.dragLocation` 冻结 → 卡死。

### 修复
1. **去掉 `.id(currentPageIndex)` 与 `.transition`**：翻页改为原地切换 `GridPageView` 的 `items`（同一实例不重建），拖拽手势所在视图得以延续。
2. **`GridPageView` 内部 `ForEach` 改用稳定身份**：行内 `ForEach(Array(rowItems.enumerated()), id: \.element)`（按 `LayoutItem` 本身，而非槽位下标）。翻页后正在拖的 app 视图被复用而非重建，手势不中断。

4. **边缘自动翻页改为"搬移"被拖 app**：新增 `flipPageWhileDragging(goNext:)`，把被拖 app 从原页移除、追加到目标页末尾，并同步 `dragState.context/sourcePageIndex/sourceSlotIndex/targetSlotIndex` 与 `currentPageIndex`，重置文件夹悬停/进度。**关键：不重建 GridPageView**，被拖 app 仍留在可见网格里，故可继续自由拖拽、松手落在第二页。

### 代价
翻页动画由"水平滑动"变为**即时切换**（`.id`/`.transition` 已移除）。功能优先于滑动特效；如需恢复滑动观感，后续可改用双页叠放 + offset 方案。`pageFlipGoingForward` 现无人读取（仅写入），属 dead 字段，暂留。

## 拖到第二页仍卡死 — 真正修复（2026-07-21，BUILD SUCCEEDED）

现象：上一轮的修复（去 `.id` + 稳定身份 + 翻页搬移 app）编译通过，但用户实测拖到第二页仍然卡死，浮动图标冻结。

### 上一轮的误判
以为「去掉 `.id` + `ForEach id: \.element` + 翻页时把被拖 app 搬到目标页」就能让手势延续。实际上：
- 拖拽手势挂在**每个 app 视图**（`AppIconView`）上；
- 翻页后 `items` 切换成新页内容，被拖 app 的原视图被 SwiftUI 从视图树移除，**即使新页 items 里又出现同一 app（通过搬移）也会重新创建视图**；
- 进行中的 `DragGesture` 随原视图销毁而取消，`onChanged` 不再触发 → 卡死。

所以问题根因不是「有没有 `.id`」，而是**手势宿主不能是被拖 app 的视图本身**。

### 真正修复
把拖拽手势宿主上移到 **GridPageView 容器层级**（覆盖整个网格），而不是每个 app 视图：
1. `GridPageView` 移除 `AppIconView` 上的 `.highPriorityGesture(cellDragGesture(item:))`。
2. `GridPageView` body 最外层加 `.simultaneousGesture(gridDragGesture())`。
3. `gridDragGesture()` 用 `DragGesture(minimumDistance: 5, coordinateSpace: .global)`：
   - 首帧根据 `value.startLocation` 查 `slotFrames` 找到起点槽位；
   - 起点是 app → 调用 `onLongPress()` 进编辑（非编辑态）、`onBeginDrag(bundleID, startLocation)`；
   - 起点不是 app（空白/文件夹）→ 忽略，让父级 `pagingDragGesture` 处理翻页/点击；
   - 拖拽中根据 `value.location` 更新最近槽位；
   - 松手时按当前页判断落点是否是 folder，决定 `onDropOnFolder` 或 `onEndDrag`。
4. `LaunchpadViewModel`：
   - `flipPageWhileDragging` 简化为只切 `currentPageIndex`（不搬移 app），因为手势宿主在 GridPageView，翻页不中断；
   - `updateDragTarget` 读取 `currentPageIndex` 判断 folder 目标，支持跨页后在新页建文件夹；
   - `endDrag` 支持跨页：从 `sourcePageIndex` 移除，插入 `currentPageIndex` 的目标槽位，并修正同页内移除后的目标索引偏移。
5. `LaunchpadView.pagingDragGesture` 增加 `!viewModel.dragState.isDragging` 条件，避免拖拽中与翻页手势竞争。

### 验证
`xcodebuild … Debug build` → **BUILD SUCCEEDED**。

## 再修：手势最终上移到 LaunchpadView 根视图（2026-07-21，BUILD SUCCEEDED）

现象：用户实测仍卡死（截图显示第二页有 folder target 高亮，浮动图标冻结）。

### 根因再定位
把手势移到 `GridPageView` 层级后仍然不行，因为 `GridPageView` 作为 `View` 其输入参数 `items` 翻页时变化，SwiftUI 仍可能重建该视图实例（即使没 `.id`），导致挂载其上的 `simultaneousGesture` 也被重置。`DragGesture` 识别器生命周期绑定到具体视图身份，视图重建即手势死亡。

### 最终方案
把网格拖拽手势放到 **LaunchpadView 根视图**（body 里最外层的 `ZStack`）。该视图在启动台显示期间身份绝对稳定，内部网格无论怎么翻页/重建都不会影响它。这是能彻底避免跨页卡死的唯一位置。

### 改动
1. `GridPageView`：彻底移除网格层级的拖拽手势（`.simultaneousGesture(gridDragGesture())` 和相关方法）。`GridPageView` 只负责渲染图标、收集 `slotFrames`、展示拖拽视觉（半透明/高亮/进度环）。
2. `LaunchpadView`：在 body 最外层 `ZStack` 加 `.simultaneousGesture(globalDragGesture())`。
3. `globalDragGesture`：
   - `DragGesture(minimumDistance: 5, coordinateSpace: .global)`；
   - 首帧用 `viewModel.nearestSlot` + `viewModel.itemAt` 判断起点是否是当前页的 app；
   - 是 app → `enterEditMode()` + `beginDrag(...)`；
   - 不是 app（空白/文件夹）→ 忽略，让 `pagingDragGesture` 处理翻页；
   - 拖动中 `updateDragTarget`；
   - 松手按当前页判断落点 folder，否则 `endDrag`。
4. `pagingDragGesture` 保留 `!viewModel.dragState.isDragging` 条件，避免拖拽中翻页竞争。

### 验证
`xcodebuild … Debug build` → **BUILD SUCCEEDED**。

### 关键结论
- 不要把跨页拖拽手势放在会随页面内容重建的视图上（单个 app、`GridPageView` 都不行）。
- 必须放在比页面切换更稳定的视图层级上，例如 `LaunchpadView` 根视图。
- 这是 SwiftUI 手势识别器与视图身份绑定的根本限制。
