## 1. 背景与可行性（重要更正）

用户希望设置页提供「导入原生 macOS 启动台布局」入口，把系统在 Launchpad 里排好的顺序与文件夹，迁移到 AppLaunchpad。

**此前误判**：曾以为 macOS 26 (Tahoe) 用新 Spotlight 取代 Launchpad、原生布局数据库已被移除，导入不可行。
**实测更正（2026-07-26）**：原生数据库仍然存在，只是路径不在旧资料所述位置。

### 1.1 真实数据库路径

```
/private$(getconf DARWIN_USER_DIR)com.apple.dock.launchpad/db/db
```

其中 `getconf DARWIN_USER_DIR` 返回形如 `/var/folders/2k/xxxx/0/` 的用户私有目录。**实测 macOS 26.5.1 该 db 文件存在（约 8.5MB）**，且为 legacy 三表 schema。

> ⚠️ 旧资料提到的 `~/Library/Application Support/Dock/desktoppicture.db` 在 Tahoe 上已不存在，不可再依赖。

### 1.2 实测 schema（用户机器）

| 表 | 列 |
|---|---|
| `apps` | `item_id, title, bundleid, storeid, category_id, moddate, bookmark` |
| `groups` | `item_id, category_id, title` |
| `items` | `rowid, uuid, flags, type, parent_id, ordering` |

- `items.type` 分布（实测）：`1=root`(2)、`2=page`(9)、`3=folder/container`(15)、`4=app`(168)
- 数据含中文标题：`音乐`、`Safari浏览器` 等 —— 正是要导入的目标。
- 另含 `app_sources / categories / dbinfo / downloading_apps / image_cache` 等辅助表，导入无需关心。

**结论**：一键导入当前系统的原生布局**完全可行**，无需用户手动提供备份文件。

```

                    ① store.backup()           // layout.json → layout.backup.json
                    ② NativeLaunchpadImporter.parseNativeLayout()  // 只读 sqlite

                    ⑥ 回主线程刷新 UI
                → 展示结果：成功 N App / M 文件夹 / 跳过 X 未安装
```

## 3. 数据源解析层

新增文件：`AppLaunchpad/Services/NativeLaunchpadImporter.swift`

### 3.1 路径与探测

```swift
import Foundation
import SQLite3

enum NativeImportError: LocalizedError {
    case databaseNotFound
    case databaseUnreadable
    case unsupportedSchema   // 非 legacy schema（如 Core Data Z* 表）
    case parseFailure(String)
}

struct NativeLaunchpadImporter {

    /// 返回 nil 表示 getconf 失败（极罕见）
    static func databasePath() -> String? {
        guard let dir = try? runGetConf("DARWIN_USER_DIR"), !dir.isEmpty else { return nil }
        return "/private\(dir)com.apple.dock.launchpad/db/db"
    }

    /// 文件存在 且 含 apps/groups/items 三表
    static func hasImportableDatabase() -> Bool {
        guard let path = databasePath(), FileManager.default.fileExists(atPath: path) else { return false }
        var db: OpaquePointer?
        guard sqlite3_open_v2(path, &db, SQLITE_OPEN_READONLY, nil) == SQLITE_OK else { return false }
        defer { sqlite3_close(db) }
        return ["apps", "groups", "items"].allSatisfy { tableExists(in: db, name: $0) }
    }

    private static func runGetConf(_ name: String) throws -> String {
        let task = Process()
        task.executableURL = URL(fileURLWithPath: "/usr/bin/getconf")
        task.arguments = [name]
        let pipe = Pipe()
        task.standardOutput = pipe
        task.standardError = pipe
        try task.run(); task.waitUntilExit()
        guard task.terminationStatus == 0 else { throw NativeImportError.databaseUnreadable }
        let data = pipe.fileHandleForReading.readDataToEndOfFile()
        return String(data: data, encoding: .utf8)?
            .trimmingCharacters(in: .whitespacesAndNewlines) ?? ""
    }

    private static func tableExists(in db: OpaquePointer?, name: String) -> Bool {
        // SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name = ?
        // （参考 LaunchNext schemaTableExists，bind_text 查询）
    }
}
```

> 只读打开 `SQLITE_OPEN_READONLY` —— 不触碰系统数据库写入，安全。

### 3.2 解析三张表

```swift
struct NativeDBApp    { let itemId: String; let title: String; let bundleId: String }
struct NativeDBGroup  { let itemId: String; let title: String }
struct NativeDBItem   { let rowId: String; let type: Int; let parentId: Int; let ordering: Int }

/// 输出：按 parent_id + ordering 重建后的、每个屏幕/页的有序 cell 序列
func parseNativeLayout() -> Result<[Cell], NativeImportError>
```

SQL（沿用 LaunchNext 验证过的写法）：

```sql
SELECT item_id, title, bundleid, storeid FROM apps;
SELECT item_id, title FROM groups;
SELECT rowid, uuid, flags, type, parent_id, ordering FROM items ORDER BY parent_id, ordering;
```

字符串列需处理 NULL（`sqlite3_column_text` 返回 nil 时给兜底值）。

### 3.3 层级重建（复用 LaunchNext 已验证逻辑）

`items` 的 `parent_id` 邻接关系：

- `type=1` 为 root（parent_id=0）
- `type=3` 且 `parent_id=1` 为顶层容器（屏幕组）
- 容器内子项含 `type=4`（直接放在屏幕上的 app）与 `type=2`（文件夹）
- `type=2`（文件夹）的子项含 `type=3`（文件夹内页/槽），其内 `type=4` 为文件夹内 app

重建算法（直接复用 `NativeLaunchpadImporter.convertAndSave` 的层级重建思路，lines 311-411）：

1. 构建 `childrenByParent: [Int: [Item]]`，每个数组按 `ordering` 升序。
2. 取 `type=3 && parent_id==1` 的顶层容器，按顺序遍历。
3. 每个容器内：
   - `directApps = children where type==4` → 直接落在该页的 app
   - `folderPages = children where type==2` → 文件夹
4. 文件夹内：取 `type=3` 子容器 → 其内 `type=4` 即文件夹内 app 列表；文件夹名取 `groups` 中的 `title`，若为占位符（untitled/folder/未命名 等）则用文件夹内前 3 个 app 名拼成 `A + B + …`。
5. 把「app / folder」按顺序塞进该页的 cell 序列。

> 之所以不复用 SwiftData 落库，是因为本项目用 `LayoutData`（`pages`/`folders`），见第 4 节。

## 4. 映射层（核心）

### 4.1 Cell 模型

```swift
enum Cell {
    case app(bundleID: String)
    case folder(name: String, appIDs: [String])
}
```

`parseNativeLayout()` 返回**扁平有序的 `[Cell]`**（跨所有原生页/屏幕拼接，保持原生相对顺序）。

### 4.2 映射目标：`LayoutData`

本项目模型（`AppLaunchpad/Models/LayoutData.swift`）：

```swift
struct LayoutData: Codable {
    var pages: [[LayoutItem]]      // LayoutItem.app(bundleID:) / .folder(id: UUID)
    var folders: [UUID: FolderInfo]
    var version: Int = 1
}
struct FolderInfo: Identifiable, Codable {
    let id: UUID
    var name: String
    var appIDs: [String]
    var isUserNamed: Bool
}
```

### 4.3 保序重流策略（已与用户确认：策略 A）

原生每页是固定网格（如 7 列×N 行），而本机 `itemsPerPage = columnCount × rowCount`（屏幕相关，可能 35~84）。
**不照搬原生绝对位置**（会留大量空格），而是：

1. 把 `[Cell]` 按本机 `itemsPerPage` 重切页；
2. app 用 `bundleID` 与本机已扫描 `data.allApps` 比对，**未安装则跳过**（记 `skipped`）；
3. folder 生成 `FolderInfo(id: UUID, name:, appIDs: 已安装子集, isUserNamed: true)`，页面放 `.folder(id:)`；
4. 文件夹内 app 同样只保留本机已安装者。

```swift
func importNativeLayout() -> NativeImportResult {
    guard NativeLaunchpadImporter.hasImportableDatabase() else { return .noDatabase }
    let cells = try NativeLaunchpadImporter.parseNativeLayout().get()

    let scannedIDs = Set(data.allApps.map(\.bundleID))
    var pages: [[LayoutItem]] = []
    var folders: [UUID: FolderInfo] = [:]
    var current: [LayoutItem] = []
    var skipped: [String] = []
    let per = itemsPerPage

    for cell in cells {
        switch cell {
        case .app(let bid):
            if scannedIDs.contains(bid) { current.append(.app(bundleID: bid)) }
            else { skipped.append(bid) }
        case .folder(let name, let bids):
            let installed = bids.filter { scannedIDs.contains($0) }
            guard !installed.isEmpty else { continue }
            let id = UUID()
            folders[id] = FolderInfo(id: id, name: name, appIDs: installed, isUserNamed: true)
            current.append(.folder(id: id))
        }
        if current.count >= per { pages.append(current); current.removeAll() }
    }
    if !current.isEmpty { pages.append(current) }

    // 导入前自动备份
    await store.backup()   // layout.json → layout.backup.json
    data.layout = LayoutData(pages: pages, folders: folders)
    data.currentPageIndex = 0
    data.saveLayout()
    return .success(apps: pages.flatMap { $0 }.count, folders: folders.count, skipped: skipped)
}
```

### 4.4 返回结果

```swift
enum NativeImportResult {
    case success(apps: Int, folders: Int, skipped: [String])
    case noDatabase
    case parseError(String)
}
```

## 7. 边界与风险

1. **schema 版本差异**：只支持 legacy 三表；若未来 macOS 改 Core Data（Z* 表），`hasImportableDatabase()` 返回 false，按钮置灰，不崩溃。
2. **数据库被系统锁定**：`SQLITE_OPEN_READONLY` 通常无碍；若打开失败，捕获错误提示「无法读取系统数据库」即可。
3. **覆盖不可逆**：导入前强制 `backup()`，UI 文案提示可还原。
4. **未安装 app**：原生有、本机无 → 跳过（不报错），结果提示跳过数量。
5. **TCC/权限**：db 在用户私有目录，App 非沙盒（需 Accessibility），只读访问用户自身数据无权限阻碍。
6. **文件夹命名占位符**：原生未命名文件夹用前 3 个 app 名生成（与 LaunchNext 一致），`isUserNamed=true` 允许用户后续改名。

## 10. 实现落地补充（开关 / 恢复默认 / 安全保障 / 体积）

### 10.1 「开关」语义（两个互斥胶囊开关）
设置页「布局」Section 改造为**两个互斥 Switch**，没有"按钮 + Toggle"那种混乱：
- **A**「使用原生 macOS 启动台布局」— `prefs.useNativeLayout = true`；db 不可用时置灰禁用。
- **B**「使用本项目默认布局」— `prefs.useNativeLayout = false`；始终可用。

互斥逻辑在 `Binding.set` 闭包里手动维持：
- 想开 A → 弹"导入系统启动台布局"确认框 → 确认后执行 `importNativeLayout()`，成功后 `prefs.useNativeLayout = true`，B 自动关。
- 想关 A → 自动开 B → 弹"恢复默认布局"确认框 → 确认后执行 `restoreDefaultLayout()`，成功后 `prefs.useNativeLayout = false`。
- 想开 B / 想关 B：对称走"恢复默认" / "导入"确认。
- 任何一步取消或失败，**`prefs.useNativeLayout` 都不会被写**，开关保持原状态，UI 不会"被偷偷改了"。

`useNativeLayout` 仍是**状态标记**，不是自动重导触发器：
- **不在每次启动自动重导**：避免覆盖用户手动调整。
- 切任意一个开关 = 一次显式的覆盖动作，由用户主动触发，绝不会被后台静默冲刷布局。

首次默认值（新用户）：
- 系统原生 db 可用 → 默认 `useNativeLayout = true`（用原生顺序铺，体验原生启动台）。
- 否则 → 默认 `false`（本项目默认布局）。`UserPreferences.init` 中实现：`d.object(forKey:) == nil` 时按 `NativeLaunchpadImporter.hasImportableDatabase()` 推算。已存在用户的偏好不受影响。

### 10.2 「恢复默认」能力
- **B 开关就是恢复默认的入口**：打开「使用本项目默认布局」会执行 `LayoutService.restoreDefaultLayout()`，用 `LayoutData.initial(from: allApps, itemsPerPage:)` 重新生成默认布局（按本机已安装 App 顺序）；同样先 `store.backup()` 再覆盖，并回主线程刷新、回到第 1 页。
- 因此两种布局可随时互转：**默认 ↔ 原生导入**，且每次覆盖前都有备份（`layout.backup.json`）可手动还原。

### 10.3 安全保障（失败绝不影响现有功能）★重点
这是用户最关心的红线，已落实为代码约束：
1. `importNativeLayout()` / `restoreDefaultLayout()` 任一失败（无数据库 `.noDatabase` / 解析异常 `.parseError` / 空结果）都**只返回错误结果**，函数内**绝不写 `data.layout`、绝不调用 `saveLayout()`**。当前布局与启动台其它功能（搜索、拖拽、翻页）完全不受影响。
2. 仅在 `parseNativeLayout()` **成功**后，才 `backup()` 再覆盖。即便覆盖后用户不满意，备份文件仍在。
3. sqlite 以 `SQLITE_OPEN_READONLY` 打开，**只读取、不写系统数据库**；系统数据零风险。
4. 解析在 `Task.detached` 后台线程（不阻塞 UI）；UI 写入 `data.layout` 回到 `@MainActor`，符合本项目"布局状态在主线"的架构约束。
5. 类型安全：跨 actor 的 `NativeCell` / `NativeImportError` 均标 `Sendable`，错误用具体类型（非 `any Error`）跨 actor，满足 Swift 6 严格并发。

### 10.4 App 体积零增长（已确认）
- 用系统 `import SQLite3`，动态链 macOS 自带的 `/usr/lib/libsqlite3.dylib`，**不打包任何第三方库、不把 8.5MB 原生 db 打进 app**。
- 唯一新增是你自己的 `NativeLaunchpadImporter.swift` 解析逻辑，编译后仅几 KB。
- 经核验：macOS SDK 提供 `SQLite3.modulemap`，`import SQLite3` 解析正常，编译通过（BUILD SUCCEEDED）。

### 10.6 后续安装 / 原生库未收录 App 的处理（绝不丢 App）★补强

**现象**：原生 Launchpad 数据库（`com.apple.dock.launchpad/db/db`）由系统启动台维护，**通常情况下会包含后续安装的 App**（系统启动台会自动收录新 App）。但存在例外，二者集合天然可能不完全一致：
- 本机已安装、但原生启动台**不收录**的 App（如外层 `.app` 无 `Info.plist` 的包裹型 App `WrappedBundle`、特殊路径安装）。
- 用户长时间未打开原生 Launchpad，数据库短暂滞后，新 App 尚未入库。
- AppLaunchpad 的扫描范围 ≥ 原生启动台，故原生库可能只是本机 App 的**子集**。

**处理（已实现，代码在 `importNativeLayout()`）**：
1. 先按原生库的 cell 顺序保序重流生成 `pages` + `folders`（原生库里有、本机也装的才进布局；原生库有但本机没装的计为 `skipped` 跳过）。
2. 计算已纳入布局的 App（含文件夹内部），得到 `coveredIDs`。
3. 取 `data.allApps`（本机已安装全集）中**未被 covered 的 App**，依次追加到末页（满页则新建一页），计为 `appended`。
4. 结论：**导入绝不会让任何一个本机已安装 App 从启动台消失**；结果文案会显示「追加 N 个本机已装但启动台未收录的 App」。

**导入之后又新装了 App 怎么办？**
- 导入只是一次性快照并写盘，不会把布局"锁死"成原生状态。导入后 AppLaunchpad 通过 FSEvents 监听 `/Applications` 等目录，触发 `refreshApps()` → `mergeLayout()`，新 App 会**自动追加到末页**（与导入时的追加逻辑同源），无需再次手动导入。
- 即分工明确：**原生布局负责"顺序与文件夹"，AppLaunchpad 自己负责"新 App 的增量补全"**，两者不冲突。
